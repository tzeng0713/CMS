# 退款管理功能規格書

本文件說明退款管理（Refund Management）功能的資料模型、業務邏輯、API 與前端操作流程，作為後續維護與驗收的依據。對應程式碼位置：

- 後端：`backend/src/main/java/com/example/cms/controller/RefundController.java`、`.../service/RefundService.java`
- 資料庫：`backend/src/main/resources/schema.sql`、`.../config/SchemaMigrationRunner.java`
- 前端：`frontend/src/app/app.component.ts`、`app.component.html`（`activeView() === 'refunds'` 區塊）、`frontend/src/app/core/cms-api.service.ts`

---

## 1. 功能總覽

| 功能 | 說明 |
|---|---|
| 新增退款 | 秘書搜尋客戶、選擇租約，填寫退款原因、退款方式與收款帳戶（皆為必填）與金額明細後建立退款單；客戶搜尋結果與租約下拉皆會排除已解約的客戶/合約（見第 7.2 節） |
| 查詢退款 | 可依公司名稱、統一編號、建立日期區間、狀態篩選 |
| 修改退款 | 僅「草稿」「待審核」狀態可修改金額相關欄位；「審核通過」狀態僅能辦理退款 |
| 取消退款 | 除「已退款」外，任何狀態皆可取消 |
| 退款審核 | 僅「主管」角色可執行，審核通過後才能辦理退款 |
| 匯入收費清單 | 從下拉選單挑選該客戶未結清的收費清單，帶出扣款金額與押金基礎金額，供新增/修改時參考填入（原為手動輸入收費清單編號，已改為下拉選單） |
| 超額扣款直接擋下 | 退款金額計算結果為負數（欠款大於可退押金）時，系統於儲存當下直接擋下、退款單不會被建立或更新，並導引秘書至收費清單管理處理欠款；退款與收費清單（收款）流程完全脫鉤，不互相關聯、不互相影響（見第 4.1、4.3 節） |
| 中途解約押金基準 | 新增/修改退款時秘書勾選「中途解約」，可退押金自動改為押金的一半（未收押金則為 0）；未勾選（合約到期解約）維持全額押金。月租金額不參與這個判斷。畫面會顯示該租約的到期日期作為參考資訊，供秘書勾選時核對，但押金基準計算仍以秘書勾選結果為準，系統不自動判斷（見第 4.1、4.1b 節） |
| 辦理退款不會回壓租約 | 退款完成（審核通過 → 已退款）**只改動退款單本身與關聯收費清單，完全不會動到租約的 `lease_status`／`termination_date_text`**，不論是否勾選「中途解約」皆同。若租約需要標記為已解約、填寫解約日期，一律由秘書自行到「租約管理」畫面手動調整（見第 4.1a 節、第 8 節） |

## 2. 資料表

### 2.1 `refunds`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `refund_id` | BIGINT PK | 退款編號 |
| `customer_id` | BIGINT FK→customers | 客戶編號 |
| `contract_id` | BIGINT FK→contracts | 租約編號 |
| `charge_list_id` | BIGINT FK→charge_lists | 關聯收費清單（選填） |
| `company_name` | VARCHAR(255) | 建立當下的公司名稱快取 |
| `refund_reason` | VARCHAR(500) | 退款原因（原欄位 `reason`，已於 migration 改名） |
| `adjustment_amount` | DECIMAL(12,2) | 手動調整金額，可正可負，預設 0 |
| `adjustment_note` | VARCHAR(1000) | 調整金額備註 |
| `deduction_total` | DECIMAL(12,2) | 扣款總金額 |
| `refund_amount` | DECIMAL(12,2) | 系統計算之退款總金額；計算結果為負數時整筆退款單會被擋下、不會存入資料庫，因此已落地的紀錄必為非負數（見第 4.1、4.3 節） |
| `mid_term_termination` | BOOLEAN，預設 `FALSE` | 秘書於新增/修改退款時勾選：`TRUE` = 中途解約，`FALSE` = 合約到期解約，見第 4.1 節 |
| `refund_status` | VARCHAR(20) | `草稿` / `待審核` / `審核通過` / `已退款` / `已取消` |
| `payment_method` / `bank_code` / `bank_account` / `bank_account_name` | | 退款方式與收款帳戶資訊，**新增退款當下即為必填**（前後端皆驗證，見第 4.1 節） |
| `refunded_at` | VARCHAR(30) | 實際退款日期 |
| `termination_staff_id` | BIGINT FK→staff | 解約經辦人 |
| `created_by` / `created_at` | | 建立人／時間 |
| `reviewed_by` / `reviewed_at` | | 審核人／時間 |
| `updated_by` / `updated_at` | | 最後修改人／時間（即「最後修改」欄位，未另外新增 `last_modified_*`） |

> 原始應退金額（押金）**不落地存成欄位**，計算當下即時從 `contracts.deposit` 讀取；若勾選中途解約，另會即時讀取 `contracts.rent` 取兩者較小值（見 4.1）。

### 2.2 退款與收費清單（`charge_lists`）完全脫鉤

`refunds.charge_list_id` 僅在秘書透過「匯入收費清單」主動挑選**既有**收費清單時才會有值（見第 7.2 節），純粹作為「這筆退款扣款金額參考哪張收費清單」的連結，供退款完成時回寫該筆收費清單為已結清（見第 3 節、第 4.4 節）之用。

除此之外，退款流程**不會**建立、修改、或以任何方式影響 `charge_lists` 資料：

- 退款金額計算結果為負數（欠款大於可退押金）時，系統直接擋下整筆退款單的儲存（不建立、不更新），**不會**自動在 `charge_lists` 建立應收帳款紀錄，也不會沿用/標記任何既有收費清單為「這筆退款的差額帳單」。詳見第 4.1、4.3 節。
- 舊版規格書中「超額扣款自動在 `charge_lists` 建立一筆 `fee_month IS NULL` 的差額帳單」的機制已完全移除，`charge_lists` 表不會再因為退款而新增任何紀錄。
- 退款與收款（收費清單）兩邊完全獨立：秘書若要處理欠款，需自行至「收費清單管理」畫面另外建立/確認收費清單並收款，與退款單的建立與否無關。

## 3. 退款狀態機

```
草稿 → 待審核 → 審核通過 → 已退款
  └──────┴──────────┴────────→ 已取消（除「已退款」外皆可取消）
```

- 「草稿」「待審核」：可自由修改所有金額與內容欄位。
- 「審核通過」：金額欄位鎖定，僅能填寫付款方式/收款帳戶/退款日期並將狀態轉為「已退款」（即「辦理退款」動作）。
- 「已退款」「已取消」：不可再修改。
- 退款完成（狀態轉為「已退款」）時，若該退款有關聯的 `charge_list_id`，系統會**回寫該筆收費清單 `status = 1`（已結清）**；完整的回壓時機（含哪些情境需要人工介入）見第 4.4 節。
- 退款完成（狀態轉為「已退款」）時，**不會**修改對應租約的 `lease_status` 或 `termination_date_text`，不論是否勾選「中途解約」皆同。合約是否已解約、解約日期為何，一律由秘書自行到「租約管理」畫面手動維護（見第 4.1a 節）。

## 4. 業務邏輯

### 4.1 金額計算（新增／修改時皆會重新計算）

```
押金基準 = 若勾選「中途解約」→ contracts.deposit ÷ 2（未收押金則為 0，等於沒有可退的押金）
           否則（合約到期解約）→ contracts.deposit（全額押金）

refund_amount = 押金基準 + adjustment_amount − deduction_total
```

- **付款資訊必填**：`payment_method`／`bank_code`／`bank_account`／`bank_account_name` 這四個欄位在**新增退款當下**就必須填寫（`RefundService.requirePaymentInfo()`），未填寫任一欄位後端回傳 `400`；前端「新增退款」表單與「修改退款」表單也同步加上 `required`，並在送出前於 `createRefund()`/`saveRefundEdit()` 額外檢查，避免漏填。舊版僅「退款原因」必填、付款資訊要到「辦理退款」步驟才要求的行為已取消。
- **中途解約押金基準**：`mid_term_termination` 這個判斷完全依賴秘書在新增/修改退款時手動勾選，系統不會自動偵測，也不會反向影響租約狀態（計算押金基準時，租約既有的 `lease_status`／`termination_date_text` 不影響此計算結果；這個勾選框現在**只**用來決定押金基準，不再觸發任何租約回壓，見第 4.1a 節）。勾選後，退款基準固定改為押金的一半（`contracts.rent` 月租金額完全不參與這個判斷，若合約簽約時未收取押金，`deposit` 為 0，基準也是 0）；已收取之預收租金本來就不在 `refund_amount` 計算範圍內（公式從頭到尾不讀 `rent_payments`），不需要另外處理。畫面上會顯示該租約的到期日期作為參考資訊，供秘書勾選時核對（見第 4.1b 節），但押金基準計算仍以秘書勾選結果為準，系統不會依到期日自動判斷或自動勾選。
  - API 回應會附帶 `message` 提示文字（例如：「中途解約，退款金額已依規定以押金的一半（NT$10000）為基準計算。」），前端直接顯示於畫面上方提示列。
- **若計算結果為負數（欠款大於可退押金）**：系統在儲存當下（新增為草稿、送交審核、或修改金額欄位）直接擋下，`RefundService.requireNotOverDeducted()` 會拋出 `RefundOverDeductedException`，這筆退款單**不會被建立或更新**（不會存成 `refund_amount = 0`，也不會嘗試寫入任何欄位）。詳見第 4.3 節。

### 4.1a 退款不會回壓租約狀態，需秘書手動維護

退款單狀態由「審核通過」轉為「已退款」（即「辦理退款」動作，見 4.2 第 4 步）時，**完全不會修改** `contracts.lease_status` 或 `contracts.termination_date_text`，不論該筆退款是否勾選「中途解約」皆同。這兩個欄位只能透過「合約/租約管理」畫面手動編輯。

> 曾經有過一版自動回壓邏輯（辦理退款時依 `mid_term_termination` 自動把租約標成已解約、寫入解約日期），後來評估後決定拿掉，改回完全手動，理由：
> - 自動回壓曾經發生過不分退款類型、一律觸發的 bug，導致單純金額調整的退款也把合約誤標為已解約。
> - 即使修正成「只有勾選中途解約才觸發」，仍然是「合約狀態被另一個功能模組的表單選項間接決定」，行為較不直觀、不易預期，且一旦寫錯難以追溯原因。
> - 改回手動後，秘書需要自行記得：合約中途解約或到期解約時，除了處理退款，還要另外到「租約管理」把 `lease_status` 改成「已解約」、填上解約日期，否則不會有任何系統提示或自動化補上（見第 8 節已知限制）。
>
> **國稅局遷出通報功能**（`TaxBureauNoticeService`）的遷出候選清單是查詢 `contracts.termination_date_text` 是否有值，因此租約解約後，秘書必須記得手動填上解約日期，該租約才會出現在遷出通報名單中；只辦理退款、不手動更新合約，是不會出現在遷出通報裡的。

### 4.1b 中途解約系統輔助提醒：顯示租約到期日參考

判斷「是否為中途解約」的機制不變，仍完全由秘書手動勾選 `mid_term_termination`，系統不會依租約到期日自動判斷、也不會自動勾選。理由：若改成系統依租約 `end_date_text`（到期日）自動判斷，當秘書提早開始辦理退款流程（尚未到期就處理合約到期解約）時，會被誤判成中途解約，導致押金退款金額被錯誤限縮為押金的一半。

新增的僅是輔助顯示：

- 「新增退款」表單：選定租約後，租約下拉下方會顯示該租約的 `end_date_text`（到期日）作為參考文字（`selectedContractEndDate()`），供秘書勾選「中途解約」前核對。
- 「修改退款」表單與「退款詳細資料」彈窗：同樣顯示該筆退款關聯租約的到期日（後端 `refundListSql()` 以 `co.end_date_text AS contract_end_date_text` 帶出，非落地存欄位，即時查詢 `contracts.end_date_text`）。
- 押金上限計算**仍完全以秘書勾選的 `mid_term_termination` 結果為準**，到期日參考資訊不會影響計算結果，也不會有任何自動勾選/取消勾選的行為。

### 4.2 審核流程（對應需求 Q17）

無論客戶是否已向國稅局登記遷出，流程一致：

1. 秘書計算退款金額、建立退款單（狀態為「草稿」或直接送出「待審核」）。若建立時選了「草稿」，之後需在退款詳細資料彈窗按「送交審核」（`PUT /api/refunds/{id}`，`refundStatus` 改為「待審核」）才能進入下一步，否則永遠停在草稿。
2. 主管於退款詳細資料彈窗按下「審核通過」（`PATCH /api/refunds/{id}/review`）。
   - 後端會查詢該員工的角色是否為「主管」，非主管回傳 `403 Forbidden`。
   - 僅「待審核」狀態可被審核，否則回傳 `400`。
   - 審核通過後寫入 `reviewed_by`、`reviewed_at`，狀態轉為「審核通過」。
3. 主管尚未審核通過前，系統不提供「辦理退款」按鈕，無法跳過審核直接完成退款。
4. 秘書於「審核通過」狀態按下「辦理退款」，填入退款日期與付款資訊後送出，狀態轉為「已退款」。

### 4.3 超額扣款處理：退款與收款流程脫鉤

退款金額計算公式不變（押金基準 + 調整金額 − 扣款總額，見第 4.1 節），但計算結果為負數時的處理方式與舊版完全不同：

- 判斷時機：新增（`RefundService.createRefund`）、送交審核、或修改金額欄位（`RefundService.updateRefund` 未鎖定金額的分支）時都會重新計算並判斷。
- 觸發條件：`押金基準 + adjustment_amount − deduction_total < 0`。
- 處理方式：`RefundService.requireNotOverDeducted()` 直接拋出 `RefundOverDeductedException`（對應 HTTP `400`），這筆退款單**不會被建立或更新**——不會存成 `refund_amount = 0`，也不會有任何欄位被寫入。
- API 錯誤回應除了 `error`（提示文字：「欠款大於可退押金，請先確認收款金額」）外，還會附帶 `chargeListId`／`customerId`／`contractId`（取自請求當下選定的收費清單/客戶/租約），供前端導引秘書快速前往收費清單管理處理欠款。前端 `extractRefundOverDeducted()` 解析這個結構化回應後，會在畫面上方顯示訊息並提供「前往收費清單管理」按鈕（`goToChargeListForRefundShortfall()`），點擊後帶著這些條件切換到收費清單管理畫面並套用篩選。
- **退款與收款（收費清單）流程完全獨立，不互相關聯、不互相影響**：退款一旦計算為負數就不會被建立，因此不會再有「超額扣款後續要處理的退款單」；秘書要處理欠款，一律透過收費清單管理畫面自行操作，與退款單無關。
- **已移除的機制**（對應舊版規格書第 4.1、4.3、4.4 節）：
  - 退款金額存為 `0`、繼續走完整審核流程（`草稿→待審核→審核通過→已退款`）。
  - 系統自動在 `charge_lists` 新建一筆差額帳單（`RefundService.createShortfallChargeList()`，已刪除）。
  - 沿用既有收費清單作為「應收帳款依據」的邏輯。

計算結果為正數時維持現行機制不變：退款單與匯入的收費清單建立關聯（`refunds.charge_list_id`），退款完成（狀態轉為「已退款」）時系統仍會自動將該收費清單標記為「已結清」（`RefundService.markChargeListSettled()`），對應第 3 節的狀態機規則。

### 4.4 收費清單狀態回壓時機一覽

「回壓」指的是把 `refunds` 的狀態變化，反映到它所關聯的 `charge_lists.status` 上。這只適用於退款當下透過「匯入收費清單」主動連結了既有收費清單的情況（見第 2.2 節）；超額扣款（負數）已於第 4.3 節改為直接擋下儲存，不會再產生新的收費清單，也就不會有相關的回壓情境。

#### ✅ 自動回壓（系統做，不需要人工另外操作）

| 時間點 | 觸發方式 | 動作 |
|---|---|---|
| 退款「審核通過」→「已退款」 | 使用者按「辦理退款」送出表單（`PUT /api/refunds/{id}`） | `updateRefund()` 在同一次請求裡呼叫 `markChargeListSettled()`，把關聯 `charge_lists.status` 寫成 `1`（已結清） |

#### ⚠️ 需要人工介入（系統不會自動處理，屬於已知限制）

| 情境 | 為什麼系統不處理 | 秘書該做什麼 |
|---|---|---|
| **退款被取消**（任何狀態按「取消」） | `cancelRefund()` 只更新 `refunds.refund_status`，完全不觸碰已連結的 `charge_lists` | 若這筆退款先前透過「匯入收費清單」連結了某張收費清單，取消後該收費清單狀態不會被改動，需自行到收費清單管理確認金額與狀態是否仍正確 |

## 5. API 一覽

| Method | Path | 說明 | 權限 |
|---|---|---|---|
| GET | `/api/refunds` | 查詢列表，支援 `companyName`/`taxId`/`dateFrom`/`dateTo`/`status`/`page`/`pageSize`/`sortBy`/`sortDir` | 無限制 |
| GET | `/api/refunds/{id}` | 查詢單筆 | 無限制 |
| POST | `/api/refunds` | 新增退款（body 含 `midTermTermination`，付款資訊四欄位為必填，見第 4.1 節；計算結果為負數時回傳 `400`，見下方說明） | 無限制 |
| PUT | `/api/refunds/{id}` | 修改退款（依狀態限制可改欄位，見第 3 節；「審核通過」→「已退款」時**不會**動到租約的 `lease_status`/`termination_date_text`，見第 4.1a 節；計算結果為負數時回傳 `400`，見下方說明） | 無限制 |
| PATCH | `/api/refunds/{id}/cancel` | 取消退款（body: `{staffId}`） | 無限制 |
| PATCH | `/api/refunds/{id}/review` | 審核通過（body: `{reviewerId}`） | 僅主管，否則 403 |
| POST | `/api/refunds/import-charge-list` | 匯入收費清單試算（body: `{chargeListId}`），回傳 `baseAmount`/`deductionTotal` 供表單預填，不寫入資料庫 | 無限制 |

**超額扣款（負數）錯誤回應**：`POST`/`PUT` 計算出的 `refund_amount` 為負數時，回傳 `400 Bad Request`，body 格式為：

```json
{ "error": "欠款大於可退押金，請先確認收款金額", "chargeListId": 123, "customerId": 45, "contractId": 67 }
```

`chargeListId`/`customerId`/`contractId` 取自請求當下選定的收費清單/客戶/租約（可能為 `null`），供前端導引秘書前往收費清單管理處理欠款（見第 4.3 節）。此情境下 `charge_lists` 表不會有任何新增或修改，退款相關的收費清單操作一律透過既有的 `GET/POST/PUT /api/charge-lists`（見 `ChargeListController`）獨立進行。

## 6. 權限模型

- 前端登入時由 `AuthService.applyPermissions()`（後端）計算 `canReviewRefund`（角色為「主管」時為 `true`），寫入 `AuthUser` 並存進 `sessionStorage`，前端用 `canReviewRefund()` 決定「審核通過」按鈕是否顯示。
- 後端 `RefundService.reviewRefund()` 會**再次以 `reviewerId` 查詢該員工角色**驗證是否為「主管」，非主管回傳 403，避免單純依賴前端隱藏按鈕。

> ⚠️ **已知限制**：本系統目前沒有 session／JWT 等伺服器端身分驗證機制，後端是「信任前端傳來的 `staffId`／`reviewerId`」去查角色，這與系統既有的 `created_by`/`updated_by` 等欄位的信任模式一致，但嚴格來說**無法防止竄改請求偽造他人身分**。若未來要做到真正安全的權限控管，需要先在整個系統補上登入態驗證（session 或 JWT），而不只是這個功能單獨處理。

## 7. 前端操作流程

### 7.1 查詢列表
- 篩選列：公司名稱、統一編號、建立日期（起訖）、狀態下拉。
- 列表僅顯示 4 欄簡單資訊：客戶／統編、退款原因、退款金額、狀態。
- 點擊任一列會開啟「退款詳細資料」彈窗，顯示完整欄位（租約編號、調整金額/備註、扣款總額、解約類型、**租約到期日參考**、建立人/時間、審核人/時間、退款方式、收款帳戶、退款日期），並依目前狀態顯示對應操作按鈕（修改／送交審核／審核通過／辦理退款／取消）。「送交審核」僅在狀態為「草稿」時出現，用來把草稿轉為「待審核」交給主管審核。

### 7.2 新增退款
1. 輸入公司名稱搜尋客戶並選擇。搜尋結果**只列出最新一筆合約非「已解約」的客戶**（`lookupRefundCustomers()`，`frontend/src/app/app.component.ts`，過濾條件 `lease_status !== '已解約'`，判斷依據與客戶管理頁的「已解約/續約中」標籤同一套邏輯，即該客戶**最新一筆**合約的狀態）；已解約的客戶不會出現在搜尋結果中。
2. 選擇該客戶的租約（下拉會顯示辦公室編號/登記＋押金金額）。此下拉只列出該客戶名下 `lease_status` 不是「已解約」的合約（`activeContracts()`），已解約的合約不會出現；若客戶同時有多筆未解約合約，會列出多個選項供分辨。選定租約後，下方會顯示該租約的到期日期（`selectedContractEndDate()`），作為秘書勾選「中途解約」時的參考資訊（見第 4.1b 節）。
3. （選填）從「匯入收費清單」下拉選單挑選該客戶**未結清**的收費清單（顯示編號／費用月份／金額），選定後按「帶入扣款金額」，自動預填扣款總額。此欄位原本是手動輸入收費清單編號的文字框，已改為下拉選單，避免打錯編號；後端 API（`POST /api/refunds/import-charge-list`）沒有變動。
4. 填寫退款原因（必填）、調整金額／備註、扣款總額、勾選「中途解約」（勾選＝中途解約、可退押金為押金的一半；不勾＝合約到期解約、退全額押金）、**退款方式與收款帳戶（銀行代碼／帳號／戶名，皆為必填，見第 4.1 節）**。
5. 選擇送出後狀態（「草稿」或「待審核」）並送出。
6. 若勾選中途解約，畫面上方會顯示押金基準已改為押金一半的提示訊息。若計算結果為負數（欠款大於可退押金），系統會直接擋下、不會建立退款單，畫面上方會顯示「欠款大於可退押金，請先確認收款金額」與「前往收費清單管理」按鈕（`goToChargeListForRefundShortfall()`），點擊後會帶著當下選定的收費清單/客戶/租約資訊切換到收費清單管理畫面（見第 4.3 節）。

### 7.3 修改／辦理退款
- 「草稿」「待審核」狀態：詳細彈窗按「修改」開啟編輯面板，可改動所有欄位（含「中途解約」勾選框），同樣顯示租約到期日參考，退款方式與收款帳戶欄位維持必填，送出時同樣會做超額扣款檢查（見第 7.2 步驟 6）。
- 「審核通過」狀態：按「辦理退款」開啟同一編輯面板，僅能填寫付款資訊與退款日期，金額欄位與「中途解約」勾選框鎖定為唯讀。送出後狀態轉為「已退款」；**合約的租約狀態與解約日期不會被自動更動**，若合約已經解約，秘書需另外到「租約管理」畫面手動修改（見第 4.1a 節）。

## 8. 已知限制 / 待辦事項

- **權限驗證非真正的伺服器端身分驗證**：如第 6 節所述，審核 API 的角色檢查是信任前端傳入的 `reviewerId`，非登入態驗證。
- **退款取消不會處理已連結的收費清單**：詳見第 4.4 節，`cancelRefund()` 只更新 `refunds.refund_status`，若這筆退款先前透過「匯入收費清單」連結了某張收費清單，取消後該收費清單狀態不會被改動，需秘書自行到收費清單管理確認。
- **押金金額為即時讀取，非鎖定快照**：計算退款金額時即時查詢 `contracts.deposit`，若之後押金被更改，既有退款單的金額不會自動重算，需手動修改。
- **「中途解約」完全依賴秘書手動勾選，系統不會自動判斷**：`mid_term_termination` 只由退款表單的勾選框決定，不會比對租約的到期日或解約日期自動判斷或自動勾選，勾錯不會有任何系統警示或驗證，需秘書自行確認。畫面雖已新增顯示租約到期日作為參考（見第 4.1b 節），但僅供核對之用，不影響判斷結果；這個勾選框目前只影響押金基準計算（押金的一半），不會再連動租約狀態（見第 4.1a 節）。
- **辦理退款完全不會回壓租約狀態，需秘書自行到租約管理手動維護**：無論一般退款或中途解約退款，`lease_status`／`termination_date_text` 都不會被自動更新，系統也沒有任何提示或待辦清單提醒秘書「這筆退款對應的合約還沒去解約」。若秘書忘記手動更新，該租約就不會出現在國稅局遷出通報名單中（因為遷出通報只認 `termination_date_text`，見第 4.1a 節）。
- **新增退款的客戶搜尋，是以「該客戶最新一筆合約」的解約狀態判斷，非逐筆合約判斷**：`lookupRefundCustomers()` 呼叫的 `customerLookup` API 只帶出每個客戶「最新一筆」合約的 `lease_status`（依 `contract_id` 取最大值），若客戶名下有多筆合約、且**最新那筆剛好已解約，但更早的另一筆合約仍在租**，這個客戶會被誤判為已解約而不出現在搜尋結果中，秘書需自行留意這種多租約客戶的邊界情況。相對地，選定客戶後的「租約」下拉是逐筆檢查每筆合約的 `lease_status`，不受此限制。
- **匯入收費清單為唯讀試算**：不會鎖定或標記該收費清單已被使用，同一張收費清單可重複匯入到多筆退款單，也沒有防止重複請款的檢查。
- **沒有防止同一租約重複建立未完成退款單**：可以對同一租約同時存在多筆「草稿/待審核」退款。
- **付款資訊四欄位皆為必填，不分退款方式**：`payment_method`／`bank_code`／`bank_account`／`bank_account_name` 在新增退款時一律必填（見第 4.1 節），系統沒有依「退款方式」（例如現金退款）做條件式必填的邏輯，即使選擇現金退款仍需填寫銀行代碼等欄位，屬既有 UI 限制。
- **超額扣款擋下時的導引連結僅為篩選條件，不保證資料仍存在**：`400` 回應附帶的 `chargeListId`/`customerId`/`contractId` 是請求當下的值，若在此之間該收費清單已被刪除或修改，前端仍會帶著這些條件切換到收費清單管理畫面，可能查無資料，需秘書自行重新確認。
- **前端沒有逐欄位的即時驗證訊息**：必填檢查多半仰賴後端回傳的 400 錯誤訊息（`branchApiErrorMessage`/`handleRefundApiError` 顯示於畫面上方）。
- **測試覆蓋**：沒有新增針對退款的專屬單元測試，驗證方式為既有 `CmsApplicationTests`（H2 profile，涵蓋完整 schema migration 與 seed data 載入）＋ `ng build` 前端型別檢查；未使用瀏覽器實際操作驗證 UI 互動細節。
