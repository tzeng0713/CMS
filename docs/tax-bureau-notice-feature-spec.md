# 國稅局通報功能規格書

本文件說明國稅局通報（Tax Bureau Notice）功能的資料模型、業務邏輯、API 與前端操作流程，作為後續維護與驗收的依據。對應程式碼位置：

- 後端：`backend/src/main/java/com/example/cms/controller/TaxBureauNoticeController.java`、`.../service/TaxBureauNoticeService.java`
- 資料庫：`backend/src/main/resources/schema.sql`（`branches.company_name`）、`.../config/SchemaMigrationRunner.java`
- 前端：`frontend/src/app/app.component.ts`、`app.component.html`（`activeView() === 'tax-bureau-notices'` 區塊）、`frontend/src/app/core/cms-api.service.ts`

---

## 1. 功能總覽

| 功能 | 說明 |
|---|---|
| 查詢本月通報名單 | 依月份（及遷離／遷入類型）自動篩選出當月應通報國稅局的公司，依「分館＋通報類型」分組顯示 |
| 勾選通報對象 | 每筆公司預設勾選，秘書可依實際情況取消勾選特定公司（例如已知作廢、找不到人等邊界情境） |
| 填寫分館通報資訊 | 每個分館群組可填寫受文者（國稅局分局）、負責人、電話；瀏覽器會記住上次填過的值，下次同分館免重填 |
| 產生並下載通報檔案 | 依勾選內容產生 `.xlsx`，比照公司既有紙本通報公文格式，每個「分館＋通報類型」各一個分頁，供秘書下載後送件 |

此功能**沒有自動排程**，全部由秘書手動在畫面上按「查詢」「產生並下載通報檔案」觸發（詳見第 8 節已知限制）。

## 2. 資料表

### 2.1 `branches`（新增欄位）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `company_name` | VARCHAR(100) | 通報公文用的法定公司全名（例如「全方位商務中心有限公司」），與 `branch_name`（分館的內部短名稱，例如「信義館」）分開存放。通報信件的「發文者」「公司」欄位優先使用 `company_name`，若未填則退回使用 `branch_name` |

`branch_code`（門牌號碼）與 `branch_address`（分館地址）為既有欄位，本功能直接沿用，不另外新增。

### 2.2 沒有新增的表／欄位

- **不新增「已通報」旗標**：不論是 `contracts` 或其他表，都沒有「這筆租約是否已經通報過國稅局」的欄位。判斷「這個月要不要通報」完全依賴 `contracts.termination_date_text`／`start_date_text` 是否落在查詢月份區間內即時計算，不落地存狀態（見第 4 節）。
- **不新增受文者／負責人／電話欄位**：這三個欄位會因「哪個國稅局分局管轄」「誰負責」而異，且非資料庫既有概念，因此**不寫入資料庫**，改為每次在前端畫面現場填寫，並用瀏覽器 `localStorage`（依分館編號存一份）記住上次填過的值，減少秘書每月重複輸入（見第 6 節）。

## 3. 通報對象判斷邏輯

### 3.1 遷離（MOVE_OUT）

- 依據：`contracts.termination_date_text` 不為空，且解析後的日期落在查詢月份區間內。
- 不論 `contracts.lease_status` 是否已經改為「已解約」，只要終止日期落在該月即視為候選對象（避免因秘書忘記切換合約狀態而漏報）。

### 3.2 遷入（MOVE_IN）

- 依據：`contracts.start_date_text` 不為空，且解析後的日期落在查詢月份區間內。
- **不會**額外判斷「是否為該客戶第一份合約」，續約／換辦公室等情境的起租日若剛好落在當月，也會出現在候選名單中，需秘書於畫面上人工勾選排除（見第 8 節已知限制）。

### 3.3 分館歸屬與未指定分館

- 透過 `contracts.office_id → offices.branch_id → branches` 取得該租約所屬分館。
- 若租約沒有指定 `office_id`（例如「登記」類型客戶常見），系統無法判斷應歸入哪個分館，這類候選人會被獨立列在「未指定辦公室／分館」清單中，**不可勾選、不可產生通報**，僅提示秘書先到租約管理補上辦公室資料。

### 3.4 日期解析

沿用系統既有的 `CmsJdbcSupport.localDate()`，同時支援 `yyyy-MM-dd`、ROC 民國格式（`yyy.MM.dd`）、`yyyy/M/d` 三種既有寫法，與租約管理其他日期欄位邏輯一致。

---

## 4. 分組規則

- 分組鍵：`分館 ID + 通報類型（MOVE_OUT / MOVE_IN）`。
- 同一分館若同時有遷離與遷入的公司，會分成兩組（對應到匯出 Excel 的兩個分頁），因為兩者的公文主旨與內文不同（見第 5.2 節）。
- 群組內公司依「通報日期 → 公司名稱」排序；群組本身依「分館名稱 → 通報類型」排序。

---

## 5. Excel 產生邏輯

### 5.1 觸發與範圍

- 前端把目前勾選的公司（`contractId` + `moveType`）與各分館填寫的通報資訊（受文者／負責人／電話）一併送到後端。
- 後端**重新用 `contractId` 查一次資料庫**取得公司名稱、統一編號、通報日期、所屬分館等權威資料，不直接信任前端傳來的公司資料內容（僅信任「選了哪些 `contractId`／`moveType`」），避免竄改請求偽造通報內容。
- 若某筆 `contractId` 找不到、沒有分館、或該通報類型對應的日期欄位是空的，直接回傳 `400` 錯誤並中止整個產生流程（不會產生部分成功的檔案）。

### 5.2 版面格式

比照公司既有紙本通報公文樣式（`受文者／發文者／發文日／主旨／說明／名單表格／公司資訊`），每個「分館＋通報類型」各自一個工作表分頁：

**遷離公文內容：**
```
         通     報
受文者 : {受文者}
發文者 : {公司名稱}
發文日 : {民國年} 年 {月} 月 {日} 日
主  旨 : 通報公司行號已遷離本址
說  明 :
一.以下公司因租約到期，並已遷離{分館地址}
二.通報名單如下

No. | 通報日期 | 門牌 | 公司名稱 | 統一編號
...

公司   :   {公司名稱}
負責人   :   {負責人}
地  址   :   {分館地址}
電  話   :   {電話}
```

**遷入公文內容：**
```
         通     報
受文者 : {受文者}
發文者 : {公司名稱}
發文日 : {民國年} 年 {月} 月 {日} 日
主  旨 : 通報公司行號遷入本址

名單如下：

No. | 通報日期 | 門牌 | 公司名稱 | 統一編號
...

公司   :   {公司名稱}
負責人   :   {負責人}
地  址   :   {分館地址}
電  話   :   {電話}
```

- 「發文日」一律採產生檔案當下的日期（`Asia/Taipei` 時區），非租約日期。
- 「公司名稱」（發文者／公司欄位）優先使用 `branches.company_name`，若該分館未填則退回使用 `branches.branch_name`。
- 「門牌」欄位使用 `branches.branch_code`。
- 字級：標題「通報」二字 36pt、粗體；其餘所有文字（含表頭與資料列）15pt，表頭另加粗體。
- 分頁名稱：遷離用門牌（例如 `221`），遷入加上「遷入」後綴（例如 `221遷入`）；若門牌未填則退回用分館名稱。名稱長度會截斷到 Excel 上限 31 字元，重複時自動加上流水號後綴。

### 5.3 下載

- 後端以 `ResponseEntity<byte[]>` 回傳，`Content-Type` 為 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`，`Content-Disposition` 帶下載檔名 `國稅局通報_{yearMonth}.xlsx`。
- 前端收到 `Blob` 後用 `URL.createObjectURL` + 觸發 `<a download>` 完成瀏覽器下載，不經過任何中介頁面。

## 6. 分館通報資訊的記憶機制

- 受文者（國稅局分局）／負責人／電話**不存資料庫**，每次產生通報檔案時由前端隨請求送出。
- 前端在使用者填寫這些欄位時，同步寫入 `localStorage`（key 為 `cmsTaxNoticeBranchInfo:{branchId}`），下次查詢到同一個分館的群組時會自動帶出上次填過的值。
- 這是**瀏覽器層級**的記憶，不同電腦／清除瀏覽器資料後需要重新輸入一次；同一分館若有多筆通報類型群組（遷離＋遷入），共用同一份記憶值。

## 7. API 一覽

| Method | Path | 說明 |
|---|---|---|
| GET | `/api/tax-bureau-notices/preview?yearMonth=YYYY-MM&type=MOVE_OUT\|MOVE_IN\|BOTH` | 查詢當月通報候選名單，依分館＋類型分組回傳，另附「未指定分館」清單。`type` 省略時預設 `BOTH` |
| POST | `/api/tax-bureau-notices/generate` | 依勾選的 `{contractId, moveType}` 清單與各分館填寫的通報資訊，產生並回傳 `.xlsx` 檔案（binary） |

## 8. 已知限制 / 待辦事項

- **完全手動觸發，沒有排程**：系統沒有 cron／`@Scheduled` 機制，「每月」通報純粹依賴秘書自己記得每月上畫面查詢並下載，系統不會主動提醒或自動寄送。
- **沒有「已通報」狀態**：同一個月內可以重複查詢、重複產生同一批公司的通報檔案，系統不會標記或阻擋重複產生，也無法從系統直接看出「這個月到底寄出去了沒」。
- **遷入名單可能包含非首次進駐的合約**：只要起租日落在當月就會出現，續約、同分館換房型等情境也會被列入，需秘書於畫面上人工勾選排除。
- **未指定辦公室／分館的租約無法通報**：這類候選人只能在畫面上看到提示清單，需先到租約管理補上 `office_id` 才能被系統正確分組，本功能不會自動猜測或修正。
- **受文者／負責人／電話僅存在瀏覽器 `localStorage`**：換電腦、換瀏覽器或清除瀏覽器資料後需要重新輸入；也代表這三個欄位沒有跨裝置同步、沒有操作紀錄可查。
- **後端以 `contractId` 重新查權威資料，但仍信任前端送來的受文者／負責人／電話文字內容**：這三個欄位會原樣寫進公文，沒有格式或必填檢查，錯字或忘記填都會直接反映在下載的檔案上。
- **沒有專屬單元測試**：驗證方式為手動以 H2 seed data 啟動後端、呼叫 `preview`／`generate` API 確認回傳內容與 Excel 內容正確，以及以 Playwright 驅動瀏覽器操作一次完整流程；未納入自動化測試套件。
